# 剪辑工作流审查

审查日期为 2026-11-25。目标是让支持本地 stdio MCP 的 agent 交付同一包装标准的短片，并能用保存的剪辑决定复刻指定版本。

## 剪映原生交付与分点动画

工作流先用配方生成可编辑草稿，给每个草稿独立的名称、ID 和实际保存位置，然后通过剪映原生窗口发起导出。文件通过画幅、帧率、帧数及异常绿帧等检查后才标为已交付。发起失败或质检失败时返回 `manual_export_required`、草稿名、绝对路径和失败原因，由用户在剪映首页打开草稿并导出。

| 剪映平台与版本 | 调用方式 | 实测范围 |
| --- | --- | --- |
| Windows 旧版（6.x 及以下） | 从首页通过可见控件查找指定草稿与导出选项。已有编辑或导出窗口时交还草稿 | 上游记录 5.9、6.8 支持此路径。[pyJianYingDraft 导出兼容表](https://github.com/GuanYixuan/pyJianYingDraft) |
| Windows 7.x 至 11.x | 匹配原生窗口、按钮和菜单模板，逐项验证后发起导出；匹配失败则交还草稿 | 上游截图基线为 11.4.2.14459、100% 缩放。本机 11.8.0.14778 已验证版本路由、草稿发布和无可交互窗口时的交接。[jianying-tool 版本说明](https://pypi.org/project/jianying-tool/0.5.0/) |
| macOS 5.x | 写入活动时间线 `draft_info.json`，使用辅助功能读取原生导出菜单 | 上游实测 5.5.0；本仓库在 Windows 上验证了 5.5.0 的时间线标记。其他 macOS 小版本需要实机验证。[jianying-tool 平台说明](https://pypi.org/project/jianying-tool/0.5.0/) |

发起导出需要可交互桌面。完成设置后由剪映渲染，MCP 等待并核验文件。安装自检用两个互相隔离的 stdio 会话迁移素材，比较同一配方生成的素材、时间线、字幕与草稿交接，报告中单独标注 `native_mp4_verified`。

“外包的优势”列表在 480 × 600、30 fps 下逐帧重放。修复前每项入场中途编号相对底色横跳约 5.81 像素，修复后测得变化不足 0.001 像素。两项各检查了入场中连续 12 对已编码帧，每对均有变化，第二项出现期间第一项保持原位。

## 从现有制作流程采用的做法

| 一手资料 | 观察到的做法 | 本项目采用的位置 |
| --- | --- | --- |

| 可重开的时间线 | 媒体、片段、轨道与关键帧可以保存在声明式项目文件中，供界面和 agent 读取。 | 定剪产物是带版本的 JSON 配方，独立记录源入点、镜头长度、字幕和素材指纹。[FableCut 项目说明](https://github.com/jcpsimmons/fablecut) |

| 设计师交付动态图形 | 设计师把动画和版式做成模板，向剪辑师开放文案、颜色等可调整字段。 | 四套风格和动效配方统一管理，agent 填标题、要点、数字或出现时间；分屏图卡按实际栏位渲染。[Adobe Motion Graphics 模板](https://helpx.adobe.com/after-effects/desktop/motion-graphics/work-with-motion-graphics-templates/creating-motion-graphics-templates.html) |
| 后期分工 | 剪辑、图形、调色、声音后期和交付有各自的工序与判断依据。 | 音轨混合、响度测量、对白复核和成片抽查分别保留证据，审片人仍可检查叙事与视觉效果。[Blackmagic Design 官方培训](https://www.blackmagicdesign.com/products/davinciresolve/training) |

## 仓库检查与修复

| 检查项 | 原先的具体风险 | 交付行为 |
| --- | --- | --- |
| 新机器和客户端 | 示例中未替换的路径会遮蔽工具发现。实际渲染依赖手动安装 npm 包、浏览器和媒体工具。 | 安装器使用主环境和桌面 CLI 各自的 uv 锁、npm 完整性锁、匹配的浏览器以及固定的语音模型和中文字体。输出含绝对路径的客户端条目。 |
| 模型操作成本 | 默认入口列出很多独立工具，指南还建议现场编写 HTML。 | `plan_video_edit` 接收剪辑字段，`deliver_video_edit` 编译、导出并验收。分屏和动效也可直接填内置配方。 |
| 素材与字幕 | 私有绝对路径难以迁移，全局转写缓存可能混入其他项目。 | 通用配方保存素材 ID、相对目录与完整 SHA-256，归档锁定字幕。批次选台词可限定 `batch_id`，高级分镜文件可指定素材根目录。 |
| 时间与落位 | 分镜用秒累计，镜头逐个取整到帧。字幕避让曾使用节目时间抽取原片，而且无字幕镜头会打乱落位报告。 | 分镜以整数帧累计，原片抽取使用源时间；每拍记录自己的落位。 |
| 包装与声音 | Python 随机化的字符串哈希改变噪声音效。宿主字体、浏览器并发和硬件编码也可能改变画面。 | 音效使用固定种子；便携渲染使用随项目携带的字体、单个绘制进程和软件编码。 |
| 失败与重试 | 编译成功容易被当作最终交付成功。 | 每次交付创建新目录。故障报告保留失败环节和已生成的文件；替换源文件的内容会在渲染前被拦下。 |

## 验收方法和适用范围

- **安装。** 用全新 Python 环境执行安装流程，检查锁定的二进制、加载本地 Whisper 模型并启动实际 Chromium。再从客户端生成的绝对路径在另一个工作目录启动服务。
- **复刻。** 安装自检在两个 stdio 会话间搬移素材并比较草稿与 SRT。拿到两次剪映原生导出的实际 MP4 后，用 `reference_review_path` 核对两版解码画面、音频与 SRT。机器、操作系统和驱动变化后需在对应机器重跑。
- **维护。** 修改配方字段时检查旧配方是否能读取。修改样式、字体、渲染器、帧换算或混音时重跑双交付。更新 OpenFilm 时同时核查两份 JavaScript 适配文件、npm 锁及对应 Playwright 浏览器；更新桌面 CLI 时单独验证其环境和上游桌面版本。
- **审片。** 根据 `review.json` 的时间码检查字是否挡脸或遮挡操作、转场是否掐断动作、原话和强调词是否准确。真峰值、综合响度与黑场是测量结果。没有有效对白或未指定交付响度时，报告保留测量情况。
- **平台。** 这轮实机覆盖 Windows x64 的本地渲染。剪映桌面导出依赖应用版本及可交互窗口；在线字体、曲库、VIP 资源和远程配音还受对应平台服务影响。

## 早期工作区渲染器实测记录

| 检查 | 观测 |
| --- | --- |
| 新环境与安装入口 | 在新的 Python 环境中完成安装，再从只含 Windows 系统目录的 PATH 调用安装器，成功启用项目内的 uv。Python 和桌面 CLI 各自的依赖锁均通过离线一致性检查。实机使用 FFmpeg/ffprobe 6.0、Node 22.20.0、OpenFilm 0.4.1 和匹配的 Chromium。 |
| 客户端接入 | 真实 MCP SDK 会话在受限 PATH 和不同工作目录下完成握手、发现工具、定剪与交付。本机 OpenCode 1.19 显示服务已连接。Codex CLI 成功读取生成的路径、环境及工具时限。VS Code 和 OpenCode 2 的配置按官方格式生成并作结构校验。[客户端配置说明与官方文档](../skills/jianying-ai-editor/references/client-config.md) |
| 横屏迁移复刻 | 640 × 360，25 fps，2.4 秒、60 帧。搬移原片与配方，在新进程重建，解码画面、声音和 SRT 全部相同。修复前曾在切点后出现一帧差异。 |
| 竖屏包装复刻 | 仓库自带素材生成 480 × 800，25 fps，4 秒、100 帧的样片。两次从独立工作目录渲染，解码画面、声音和 SRT 三项 SHA-256 相同。0.68 秒抽帧只显示“选择原话”，2.04 秒抽帧显示第二项“对齐画面”，章节镜头和中文字幕均可见。[可复用的分屏参数](../examples/edits/packaged-interview.json) |
| 原声与审片 | 离线 Whisper small 在中文语音样本中返回两段带时间码的文本，也把专名“剪映”听成了“简硬”。定剪可传经确认的文案；生产审片应复听专名、数字和关键结论。 |
| 自动化回归与发行包 | 源码回归 169 项通过、147 个子测试通过，1 项因缺少加密草稿样本跳过。将构建的 wheel 单独安装后，隔离解释器运行同一组 170 项测试并通过可执行项，另从源码目录外完成两次真实 stdio 交付。横屏样片的解码指纹与正式安装环境一致。 |
| 版本与可编辑交付 | 输出的 MP4、SRT、配方、草稿、抽帧及报告集中在独立交付目录。实机发现自定义路径上的剪映专业版 11.8.0.14778，桌面 CLI 为 0.5.0，桌面导出适配器的基线为 11.4.2.14459。本轮 MP4 通过随附渲染器实际导出。 |

上述双跑使用同一台 Windows x64 机器。对另一台机器的复刻，可将已验收的 `review.json` 作为 `reference_review_path` 提交，工具会分别给出解码画面、音频和 SRT 的比较结果。面向新题材的选段、叙事顺序和视觉质量，需要结合源内容审片。

## 早期 OpenFilm 绿帧问题回归

| 项目 | 复核结果 |
| --- | --- |
| 宿主接入和代表帧 | 安装后的命令行可通过 stdio 和本机 HTTP 发起相同的 MCP 调用。回归覆盖宿主与安装配置指向不同运行目录的情况，并检查抽取代表帧时媒体子进程的标准输入已隔离。重复画面只写入选中的 JPEG。 |
| 批量对白 | 一个已有的 37 段素材批次通过 `export_media_batch_transcript` 导出 265 条带原片时码的对白。回归还覆盖旧缓存缺失和长台词完整导出的情况。 |
| 导出绿帧 | 实际竖屏工程共 4,166 帧。旧 MP4 的 9 个时段有 2,580 帧大面积纯绿。用工程预览的绘制路径重渲后，4,166 帧中疑似绿帧为 0，解码音频和 SRT 指纹与旧版一致。从同一问题素材单独截取 3 秒，经已安装的 `deliver_video_edit` 自动检出首轮 90 帧全绿、对照工程预览并重渲，第二轮 90 帧均通过。 |

涉及有意绿底、重渲后仍有异常、媒体不可读与扫描不完整的自动验收见[现场问题回归测试](../tests/test_runtime_feedback.py)。
